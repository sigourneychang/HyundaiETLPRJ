# Hive → Hive 클러스터 이관 도구: 개발 사양 노트

이 문서는 운영 환경을 기준으로 이관 도구를 구현하거나 고칠 때 참고하는 사양입니다. 이 문서만 읽어도 맥락을 알 수 있게 썼으므로, 사람이든 AI 코딩 도구든 그대로 따르면 됩니다.

표기 규칙
- **[필수]**: 지켜야 하는 규칙. 어기면 데이터가 손상되거나 운영에 영향을 줍니다.
- **[권장]**: 기본 설계. 바꿀 때는 이유를 문서에 남깁니다.
- **[확인]**: 프로젝트를 시작한 뒤 운영 환경에서 확인해야 하는 항목.

---

## 1. 목표와 제약

| 항목 | 내용 |
|---|---|
| 목표 | 원본 Hive 클러스터의 DB나 테이블을 별도의 대상 Hive 클러스터로 이관하고, 원본과 대상이 같은지 검증 |
| 이관 단위 | DB 전체 또는 테이블 목록. 테이블 이름은 그대로, DB 이름은 바꿀 수 있음(DB 단위) |
| 버전 | 양쪽 모두 Hive 2.x. Hive 3과 4의 기능(예: 기본 ACID, `REPL`)은 쓰지 않음 |
| 규모 | 약 500TB, 테이블 수만 개, 기간 약 4개월. 작은 테이블이 대부분이고 큰 테이블이 일부라고 가정 |
| 실행 위치 | **대상 클러스터 엣지 노드** |
| 원본 접근 | ① beeline으로 원본 HiveServer2에 SQL 조회 ② `hadoop fs`와 distcp로 원본 HDFS 읽기. **원본 메타스토어 DB에는 직접 접속하지 않음** |
| 원본 운영 | 원본은 이관 기간 동안 고정(쓰기 없음)이지만 운영 중. **원본 부하와 원본 쓰기를 최소화**해야 함 |
| 보안 | Kerberos 없음 |
| 구현 제약 | Python 3.6 이상, **표준 라이브러리만** 사용(엣지 노드에 pip 설치가 안 될 수 있음). 외부 CDN 없음 |
| 범위 | 테이블 DDL과 데이터, 뷰. **범위 밖**: 권한(GRANT, Ranger, Sentry), 테이블 소유자(대상에서는 도구 실행 계정이 됨), 파티션 수준 통계, 함수(`CREATE FUNCTION`), DB 속성과 코멘트 |

**[확인]**
- 원본과 대상의 Hadoop 버전. 다르면 distcp는 `webhdfs://`를 씁니다.
- 클러스터 간 네트워크와 방화벽: NameNode RPC/HTTP 포트, DataNode 포트
- 원본 HiveServer2에서 허용되는 작업: 조회 외에 아래 6장의 원본 쓰기 2가지가 허용되는지
- 운영 HiveServer2의 동시 세션 처리 능력 (병렬 수 결정)
- 대상 클러스터의 YARN 사용 여부와 큐
- **원본이 정말 고정인지**: 인벤토리의 `last_change`와 요약의 "changed in the last N days"(기본 30일, `--recent-days`)로 확인합니다. 최근에 바뀐 DB가 있으면 원본 운영팀과 DB별 쓰기 중단 시점을 정하고 그 뒤에 이관합니다. 정하기 어려우면 전환 직전에 그 DB를 다시 이관합니다.
  - `last_change`는 `ddl_time`(테이블의 `transient_lastDdlTime`)과 `dir_mtime`(테이블 폴더의 수정 시각) 중 늦은 값입니다. 둘 다 원본 쿼리 없이 얻습니다(`DESCRIBE`, `hadoop fs -stat`).
  - 폴더 수정 시각은 폴더 바로 아래 항목(파일, 파티션 폴더)이 추가, 삭제, 교체될 때만 바뀝니다. **기존 파티션 폴더 안에 파일만 추가되는 쓰기는 잡히지 않습니다.** 이런 경우는 전환 직전의 변경 감지(9장)로 잡습니다.
- ACID 테이블 수와 크기: 인벤토리 요약의 ACID 항목. 6장의 원본 쓰기 승인을 받을 때 함께 제시합니다.

## 2. 구성

| 파일 | 역할 |
|---|---|
| `migrate/hive_migrate.py` | 이관, 검증, 대상 삭제 CLI. 웹 화면도 이 프로그램을 실행함 |
| `migrate/hive_inventory.py` | 원본 인벤토리(읽기 전용). 테이블별 종류, 형식, 파티션, 경로, 크기, 파일 수, 마지막 변경 시각을 CSV로 남기고 이관 목록(`sources.csv`)을 만듦. 요약에 최근 변경된 DB와 ACID 수, 크기를 보여줌 |
| `migrate/web_ui.py` + `migrate/web/index.html` | 웹 화면 (`http.server`, 기본 127.0.0.1:8080, 원격에서는 SSH 터널로 접속) |
| `conf/*.ini` | 클러스터 접속과 실행 옵션 |
| `reports/` | 실행 로그(`migration_<run_id>.log`), 결과 CSV(`migration_<run_id>.csv`), 인벤토리, 웹 작업 출력 |

```bash
python3 migrate/hive_inventory.py -c conf/prod.ini --all
python3 migrate/hive_migrate.py   -c conf/prod.ini -s sources.csv [--dry-run] [--parallel N] [--control FILE]
                                  [--if-exists replace|skip|fail] [--validate checksum|count|none] [--repair-source true|false]
python3 migrate/hive_migrate.py   -c conf/prod.ini -s list.csv --drop-target [--drop-databases db1,db2] [--dry-run]
python3 migrate/web_ui.py         -c conf/prod.ini [--host 127.0.0.1] [--port 8080]
```

## 3. Hive 2.x 이관의 함정 (설계의 근거)

| # | 함정 | 대응 |
|---|---|---|
| 1 | **ACID 테이블을 파일로 복사하면 깨짐.** delta 디렉터리는 클러스터 전역 트랜잭션 ID를 쓰므로 대상에서 조회가 안 되거나, 이후 INSERT 때 행이 사라짐 | **[필수]** ACID(`transactional=true`)는 파일 복사 금지. 원본 스테이징(일반 ORC)으로 `INSERT … SELECT` → distcp → 대상에서 `INSERT INTO` |
| 2 | 새로 만든 managed 테이블은 통계가 `numRows=0`, `COLUMN_STATS_ACCURATE=true`라서, 파일을 복사해도 `count(*)`가 통계값 0을 돌려줌 | **[필수]** 원본 통계가 정확하면 통계를 복사하고, 아니면 `COLUMN_STATS_ACCURATE=false`로 표시. 검증 때 통계 기준 `count(*)`도 확인 |
| 3 | 대상 디렉터리가 이미 있으면 distcp가 그 아래에 한 단계 더 중첩해서 복사함 | **[필수]** distcp에 항상 `-update`. 지우고 다시 만들 때는 `-delete` 추가 |
| 4 | `SHOW CREATE TABLE`의 `LOCATION`은 원본 경로 그대로 | external 테이블과 사용자 지정 경로는 경로를 유지(DB 이름을 바꾸면 경로의 DB 부분도 바꿈). 기본 경로의 managed 테이블은 `LOCATION`을 빼고 대상 warehouse 기본 경로를 씀 |
| 5 | MSCK는 ACID 테이블을 고치지 못함 | ACID는 1번 방식으로 처리 |
| 6 | Hive 2.3의 HiveServer2는 `MSCK TABLE`(검사만)의 결과를 beeline에 돌려주지 않음 | 파티션 누락 판단은 `SHOW PARTITIONS` 개수 비교와 HDFS 폴더 수로 함 |
| 7 | beeline `-e`에 SQL을 넘기면 인자 한 개가 128KB를 넘을 때 실패하고, 앞이 `--` 주석이면 아무것도 실행하지 않음 | **[필수]** SQL은 stdin으로 넘김(`-f /dev/stdin`) |
| 8 | beeline은 문자열 안의 `;`도 문장 구분자로 자름 | 문자열 리터럴 안의 `;`는 `\073`으로 바꿈. Hive 문자열은 따옴표를 겹쳐 쓰는 대신 백슬래시로 이스케이프 |
| 9 | **연결이 끊겨도 beeline이 rc=0과 빈 출력을 돌려줄 수 있음** | **[필수]** 결과 구역 마커가 빠지면 "0행"으로 읽지 말고 오류로 처리 |
| 10 | 오래 걸리는 쿼리에서 beeline stdout에 `' \r'`(진행 표시를 지우는 줄)가 결과 앞에 끼어듦. `--silent=true`로도 막히지 않음 | **[필수]** 출력은 `\n`으로만 나누고 끝의 `\r`을 떼며, 공백뿐인 줄은 버림. `splitlines()`처럼 `\r`, `\x0b`, `\x1c`~`\x1e`, `\x85`, `\u2028`에서도 자르는 함수는 쓰지 않음 |
| 11 | 여러 결과를 한 세션에서 받을 때 어느 줄이 어느 결과인지 모름 | 결과 사이에 `SELECT '@@NAME@@'` 마커 문장을 넣고 마커로 나눔 |
| 12 | `ALTER TABLE … SET TBLPROPERTIES`로 넣은 통계(`numRows`와 `COLUMN_STATS_ACCURATE=true`)를 Hive 2.3은 "정확하지 않음"으로 바꿈(`COLUMN_STATS_ACCURATE`가 사라짐). 통계를 복사해도 대상의 `count(*)`는 데이터를 읽음 | 결과는 맞으므로 검증에는 영향 없음. 통계 기준 `count(*)` 확인은 계획만 보고 판단(5장). **[확인]** 운영 Hive 버전에서도 같은지, 대상 사용자 쿼리에 정확한 통계가 필요하면 `ANALYZE`를 따로 돌릴지 |

## 4. 처리 흐름 (`hive_migrate.py`)

### 4.1 입력
- `sources.csv`: 헤더 `db,table[,tgt_db]`
  - `table`이 `*`면 DB 전체입니다.
  - `tgt_db`가 비어 있으면 원본과 같은 DB 이름을 씁니다.
  - `#`으로 시작하는 줄은 주석입니다.
  - 이름은 `[a-z0-9_]`만 씁니다(Hive는 소문자로 저장).
- **[필수] 실행 전 검사**
  - 원본 DB 하나를 두 개의 대상 이름으로 지정하면 실행하지 않습니다.
  - 여러 원본 DB를 한 대상 DB로 모을 때 테이블 이름이 겹치면 실행하지 않습니다.

### 4.2 1단계: 준비 (명령 기동 비용을 줄이려고 묶어서 실행)
1. `*`로 지정한 DB는 원본에서 `SHOW TABLES`로 펼칩니다.
2. 원본에서 `SHOW CREATE TABLE`과 `DESCRIBE FORMATTED`를 **한 beeline 세션에 최대 `meta_batch`(50)개씩** 조회합니다. 묶음이 실패하면 그 묶음만 테이블별로 다시 조회합니다.
3. 테이블을 분류합니다.
   - VIEW: `VIRTUAL_VIEW`
   - 미지원: DDL에 `STORED BY`가 있음
   - ACID: `transactional=true`
   - EXTERNAL / MANAGED
4. 대상에서 DB 위치(`DESCRIBE DATABASE`)와 warehouse 경로를 읽어 managed 테이블의 대상 경로를 미리 계산합니다.
5. 원본 테이블 경로와 대상 경로를 `hadoop fs -count`로 **한 번에 최대 100개씩** 조회해 폴더 수, 파일 수, 크기를 얻습니다. 원본 경로는 대상 엣지 노드에서 `[src] hdfs_uri`를 붙여 조회합니다.
6. **빈 테이블 판정**: 원본 폴더에 파일이 0개이고, 파티션이 없고, 대상 경로에 예전 파일이 없으면 빠른 처리 대상입니다.

### 4.3 2단계: 이관 (작업자 풀 1개)
- 테이블과 뷰를 작업자 풀 하나(`parallel`, 기본 2)에서 처리합니다. 운영 원본에는 작은 테이블이 거의 없을 것으로 보고 크기별로 풀을 나누지 않습니다. **[확인]** 운영 인벤토리에서 작은 테이블과 빈 테이블 비율을 확인하고, 많으면 크기별 풀 분리를 다시 검토합니다.
- **[필수] 실행 중 동시 처리 수 변경**: 실행을 멈추지 않고 `parallel`을 바꿀 수 있어야 합니다. 이관 프로세스가 제어 파일(`--control`, JSON `{"parallel": N}`)을 몇 초마다(파일 수정 시각이 바뀔 때만) 다시 읽습니다. 늘리면 바로 작업을 더 넣고, 줄이면 진행 중인 테이블은 끝까지 두고 새로 넣는 수만 줄입니다. 범위는 1~64입니다. 파일을 읽지 못하거나 값이 잘못되면 현재 값을 유지합니다. 제어 파일은 임시 파일에 쓴 뒤 이름을 바꿔(원자적 교체) 반쯤 쓰인 내용을 읽지 않게 합니다. 운영에서는 원본 부하를 보며 낮에는 줄이고 밤에는 늘리는 용도입니다.
- **[필수] 원본 검증값 조회는 대상 작업과 동시에 실행합니다**(ACID 제외).
  - 원본 조회는 대상 쪽 단계와 결과를 주고받지 않으므로, 기다리면 테이블 하나 시간이 원본 조회만큼 늘어날 뿐입니다.
  - 원본 조회 결과를 기다리지 않으므로 행 수가 0이어도 distcp를 합니다. 파일이 하나도 없는 테이블은 빠른 처리로 먼저 빠집니다.
  - 판정 전에 원본 조회가 끝나기를 기다립니다. 어느 쪽이 실패해도 원본 조회가 끝난 뒤 대상 테이블을 되돌립니다. 원본 조회가 실패하면 대상이 끝났어도 되돌립니다.
  - ACID는 원본 스테이징 작업이 있어 원본 조회 → 스테이징 → 대상 순서로 차례대로 합니다(원본에 동시에 두 작업을 띄우지 않음).
  - 작업자 하나가 원본과 대상에 명령을 하나씩 동시에 띄울 수 있습니다. 동시 처리 수를 정할 때 감안합니다.
- **[필수] 작업은 미리 큐에 다 넣지 않습니다.** 풀에 빈 작업자가 생길 때마다 하나씩 넣고, 이때 참조 객체가 끝난 뷰를 남은 테이블보다 먼저 넣습니다. 미리 다 넣으면 뷰가 남은 테이블 수천 개 뒤에 줄을 서서, 실행이 끝날 때까지 DB마다 뷰만 남습니다.

| 경우 | 처리 |
|---|---|
| 대상에 이미 있음 | `if_exists`: **replace(기본, 지우고 다시 만듦)** / skip / fail |
| **빈 테이블** | 대상에서 한 세션으로 생성 → 통계 설정(0행, 정확함) → 통계 기준 `count(*)`가 0인지 확인. 원본 쿼리와 distcp 생략 |
| 일반 테이블 | 원본 검증값 조회와 동시에: 대상 생성(+`DESCRIBE`) → 경로 확인 → distcp → `MSCK REPAIR`(파티션 테이블) → 통계 → 대상 검증값 조회. 둘이 끝나면 판정 |
| ACID | 원본 스테이징 DB(`zz_migration_stage`)에 일반 ORC로 `INSERT OVERWRITE` → distcp → 대상 스테이징 → 대상 ACID 테이블에 `INSERT INTO` → 양쪽 스테이징 삭제 |
| 파티션 테이블, 원본 0행 | 원본에 등록 안 된 파티션 폴더가 있을 수 있음. 파티션 컬럼이 1개이고 "테이블 폴더 아래 폴더 수 = 원본 파티션 수"이면 정상으로 보고 넘어감. 아니면 `repair_source=true`일 때 원본 `MSCK REPAIR` 후 다시 셈 |
| VIEW | 뷰 DDL이 참조하는 객체 중 이번 실행에 포함된 것이 끝나는 대로 생성. 이번 실행의 DB 이름 대응표 전체를 뷰 본문에 한 번에 적용. 실패하면 마지막에 한 번 더 시도 |
| 미지원 (`STORED BY`) | 이관하지 않고 `UNSUPPORTED`로 기록 |

**DB 이름 바꾸기**
- managed 테이블의 기본 경로는 대상 DB 기본 경로가 됩니다.
- external 테이블과 사용자 지정 경로는 경로 중 원본 DB 이름과 같은 부분(`<db>` 또는 `<db>.db`)을 바꿉니다. 경로에 DB 이름이 없으면 그대로 두고 메시지에 남깁니다.

### 4.4 안전장치
- **[필수] 대상 경로에 다른 파일이 있으면 이관하지 않습니다.** 지우고 다시 만드는 경우는 예외입니다.
- **[필수] 되돌리기**: 대상 테이블을 만든 뒤 실패하거나 중지되면, 대상 테이블(external은 파일까지)과 스테이징을 지우고 비게 된 상위 폴더도 정리합니다.
  - 이유: 반쯤 만든 테이블이 남으면 다음 실행이 "이미 있음"으로 보고 건너뛸 수 있습니다.
  - 검증 불일치(MISMATCH)는 조사할 수 있도록 남깁니다.
- **[필수] 공용 경로 보호**: `/`, `/data` 같은 2단계 미만 경로, warehouse 루트, `*.db`, 해당 DB의 위치 폴더는 지우지 않습니다.
- **연결 실패 재시도**: beeline이 세션을 열지 못한 경우("Could not open client transport", "Connection refused", "Failed to open new session" 등)는 SQL이 실행되지 않은 상태라 쓰기 명령도 재시도합니다. 간격은 10초, 20초, 40초, 60초입니다.
  - 실행 중에 끊긴 명령은 일부가 실행됐을 수 있으므로 재시도하지 않고 되돌립니다.
  - 읽기 전용 호출이 시간 초과되면 `retries`만큼 다시 시도합니다.
- **명령 시간 제한**: beeline은 `call_timeout`(900초), distcp는 `[distcp] timeout`(7200초)입니다.

### 4.5 중지 (신호)
| 신호 | 동작 |
|---|---|
| `SIGUSR1` | 진행 중인 테이블은 끝까지 하고, 새 테이블은 시작하지 않음 |
| `SIGTERM` / `SIGINT` (프로세스 그룹) | 진행 중인 명령을 끊고 되돌림. YARN에 남은 이번 실행의 distcp 작업을 이름으로 찾아 `yarn application -kill`. distcp에는 `-Dmapreduce.job.name=hive_migrate_<run_id> <db.table>`을 붙임 |

중지해도 결과는 기록합니다. 시작하지 못한 테이블은 `STOPPED`로 남깁니다.

### 4.6 대상 삭제 (`--drop-target`)
- **[필수] 대상 클러스터만** 건드립니다. 지우기 직전에 `DESCRIBE FORMATTED`로 종류와 경로를 다시 확인합니다.
- **[필수] 목록의 `db` 열은 대상 DB 이름입니다.** `tgt_db` 열에 `db`와 다른 값이 있으면 실행하지 않습니다. 이관용 목록(원본 이름 + `tgt_db`)을 그대로 넣으면 원본과 같은 이름의 대상 테이블이 지워지기 때문입니다.
- 종류별 처리
  - managed, ACID: `DROP TABLE … PURGE`
  - external: `DROP TABLE` 후 경로 삭제(`-skipTrash`)와 빈 상위 폴더 정리
  - view: `DROP VIEW`
  - 대상에 없음: `DROPPED`로 기록
- `--drop-databases`는 테이블을 다 지운 뒤 **DB가 비어 있을 때만** `DROP DATABASE`(CASCADE 없음)를 실행합니다.

| 모드 | 원본과 대상에서 실행 | 비고 |
|---|---|---|
| **checksum (기본)** | `SELECT count(1), sum(hash(*))` | 내용까지 비교. **양쪽 전체 데이터를 읽음** |
| count | `SELECT count(1)` | |
| none | (파티션 목록만) | |

- 행 수를 셀 때는 `SET hive.compute.query.using.stats=false`로 통계가 아닌 실제 데이터를 읽습니다.
- 대상에서는 추가로 사용자가 `count(*)`를 했을 때(`hive.compute.query.using.stats=true`) 돌려받는 값이 실제 행 수와 같은지 확인합니다.
  - **[필수] 이 확인으로 데이터를 다시 읽지 않습니다.** 같은 세션에서 `EXPLAIN SELECT count(*)`만 실행합니다(작업 없음).
  - 계획에 실행 단계(`Map Reduce`, `Tez`, `Spark`)가 있으면 Hive가 데이터를 읽어 답하므로 값은 실제 행 수와 같습니다. 쿼리를 따로 돌리지 않습니다.
  - 실행 단계가 없으면(`Fetch Operator`만) 통계로 답하는 것이므로, `SELECT count(*)`로 그 값을 가져와 비교합니다(메타스토어 조회, 작업 없음).
  - 계획에 `STAGE PLANS`가 없으면 읽지 못한 결과로 처리합니다(아래 [필수]).
- 파티션 테이블은 모드와 관계없이 `SHOW PARTITIONS` 목록을 이름 단위로 비교합니다.
- 판정: 위 항목이 하나라도 다르면 `MISMATCH`, 모두 같으면 `OK`입니다. 뷰는 행 수만 비교합니다.
- **[필수] 결과를 읽지 못한 것은 불일치가 아닙니다.** 결과 구역이 없거나 비어 있으면 연결 오류로 처리합니다. 행 수 자리가 숫자가 아니면 원문을 로그에 남기고, 읽기 전용인 검증 쿼리만 한 번 더 실행합니다. 대상 쪽 앞 단계(ALTER, MSCK, ACID INSERT)는 다시 실행하지 않습니다. 두 번째도 읽지 못하면 `FAILED`로 처리합니다.

## 7. 인터페이스

### 7.1 설정 (INI)
**필수**: `[src] beeline, hdfs_uri` / `[tgt] beeline, hadoop`

| 키 | 기본값 | 설명 |
|---|---|---|
| `[src] hadoop` | – | 인벤토리용. 원본 크기 조회(읽기 전용) |
| `[tgt] hdfs_uri` | `''` | 대상 기본 FS |
| `[tgt] yarn` | hadoop 명령에서 유도 | 중지 시 YARN 작업 종료용. 빈 값이면 사용 안 함 |
| `[distcp] command / options / timeout` | `<tgt hadoop> distcp` / `-update -m 20` / 7200 | 원본 부하 제한: `-bandwidth`, `-m`. 버전이 다르면 `-pb` 또는 `-skipcrccheck` 검토 |
| `[run] parallel` | 2 | 테이블과 뷰를 동시에 처리하는 수 |
| `[run] if_exists` | replace | replace / skip / fail |
| `[run] validate` | checksum | checksum / count / none |
| `[run] stats` | copy | copy / analyze / none |
| `[run] repair_source` | true | 6장 참고 |
| `[run] meta_batch` | 50 | 준비 단계 메타정보 묶음 크기 |
| `[run] call_timeout / retries / max_dynamic_partitions` | 900 / 2 / 100000 | |
| `[inventory] batch_size / path_batch_size` | 200 / 100 | `path_batch_size`는 이관 준비 단계의 경로 묶음에도 씀 |
| `[staging] db` | zz_migration_stage | ACID용 (양쪽 클러스터) |
| `[result] db / table` | migration_meta / migration_result | 대상 클러스터 |

beeline과 hadoop 명령은 셸 문자열로 받습니다. 예: `beeline -u jdbc:hive2://host:10000/ -n user`

### 7.2 결과
- **결과 테이블** (대상): `run_id string, migrated_at timestamp, src_db, src_table, tgt_db, tgt_table string, src_count, tgt_count bigint, is_match boolean, status string`
  - 실행이 끝나면 `INSERT … VALUES`로 한 번에 기록합니다.
  - **[권장]** 테이블 수가 많으면 일정 건수마다 나눠 쓰고, `run_id`로 파티션을 나눕니다(미구현).
- **결과 CSV**: `src, tgt, kind, partitioned, status, src_rows, tgt_rows, tgt_count_star, src_checksum, tgt_checksum, src_partitions, tgt_partitions, seconds, message`
  - **[필수] 실행 중 2초마다 끝난 객체를 다시 씁니다**(임시 파일에 쓴 뒤 이름 바꾸기). 프로세스가 강제로 죽어도 대상에 한 일이 기록에 남아야 합니다.
- **상태값**: `OK`, `MISMATCH`, `FAILED`, `STOPPED`, `SKIPPED`, `UNSUPPORTED`, `DRY-RUN`, `DROPPED`
- **종료 코드**: 0(모두 OK, SKIPPED, DRY-RUN, DROPPED), 1(그 외 상태가 있음), 2(준비 단계에서 중단)
- **로그 형식**: `HH:MM:SS [db.table] 메시지`. 객체마다 마지막 줄은 `=> <STATUS> <메시지>`입니다. 웹 화면은 이 형식을 파싱하므로 형식을 바꾸면 화면도 함께 고쳐야 합니다.
  - 준비 단계 진행 표시는 `metadata ok (<종류>)`
  - 이관 단계 시작 신호는 `[plan] tables=…`

### 7.3 웹 화면 API (`web_ui.py`)
| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/info` | 설정 파일, 인벤토리 정보 |
| GET | `/api/source/dbs`, `/api/source/tables?db=`, `/api/source/search?q=` | 원본 트리. **최신 인벤토리 CSV에서 읽음**(원본을 실시간으로 조회하지 않음) |
| GET | `/api/target/dbs[?refresh=1]` | 대상 실제 DB, 테이블 목록(`SHOW DATABASES`, `SHOW TABLES`, DB 200개씩 묶음, 5분 캐시). `default`와 도구용 DB는 제외 |
| GET | `/api/history` | `{target: 대상 이름별 현재 상태, attempts: 원본 이름별 마지막 시도}` (결과 CSV 기반) |
| GET | `/api/job?offset=` | 실행 중이거나 마지막 작업의 상태, 로그, 테이블별 진행 |
| POST | `/api/migrate` | `{items:[[db,table,tgt_db]], dry_run, if_exists, validate, parallel, repair_source}` |
| POST | `/api/parallel` | `{parallel}`: 실행 중인 이관의 동시 처리 수 변경(제어 파일을 다시 씀). 실행 중인 이관이 없으면 400 |
| POST | `/api/drop` | `{items:[[tgt_db,table]], drop_dbs:[…], confirm:"삭제"}`. 확인 값이 없으면 거부 |

POST는 JSON만 받습니다. 이름은 `[A-Za-z0-9_]`만 허용하고, 서버는 기본으로 127.0.0.1에만 엽니다.

### 7.4 웹 화면의 동작 규칙
- **화면 구성**: 가로 3칸(원본 | 이관 목록 | 이관 결과)과, 원본과 이관 목록 사이의 추가·제외 버튼 줄로 이뤄집니다. 각 칸은 위에서부터 다음 순서입니다.
  1. 제목과 기능 버튼(한 줄 고정)
  2. 모두 펼치기·접기, 검색, 필터(한 줄)
  3. 트리
  4. 맨 아래 줄: 요약 숫자와 칸 설명
  - 세 칸의 검색 줄과 트리 시작 높이가 같아야 합니다.
- 원본 트리에서 DB 이름이나 체크박스를 누르면 선택만 하고, 펼치기와 접기는 앞의 화살표로만 합니다. DB 여러 개를 연달아 고르기 위해서입니다.
- **[필수] 이관 결과 칸은 대상 클러스터의 실제 테이블 목록이 기준입니다.**
  - 상태와 행 수는 결과 CSV에서 붙입니다.
  - 기록이 없는 테이블은 "도구 기록 없음", 테이블이 없는 DB는 "빈 DB"로 표시합니다.
  - 기록에만 있는 테이블은 표시하지 않고 개수만 안내합니다.
  - 테이블을 만들기 전에 실패한 것은 결과에 나오지 않고, 이관 목록과 원본 트리에서 "마지막 시도" 상태로 봅니다.
  - 이관 실행 중에는 다음과 같이 맞춥니다.
    - 이번 실행에 들어 있고 아직 차례가 오지 않은 테이블은 지난 결과(OK, 행 수)를 지우고 "이관 대기"로만 표시합니다. 차례가 되면 지우고 다시 만들기 때문입니다. 대상에 실제로 있는 것만 보입니다.
    - 진행 중(RUNNING)인 테이블은 결과 칸에서 숨깁니다. 대상에 만들어지고 있지만 아직 결과가 없는 상태라 "도구 기록 없음"으로 잘못 보이기 때문입니다. 진행 상태는 이관 목록 칸에서 봅니다.
    - 방금 OK나 불일치로 끝난 테이블은 작업 상태(`/api/job`의 items)로 바로 표시합니다. 그 DB가 대상 목록에 아직 없어도 있는 것으로 봅니다.
    - 대상 목록과 결과 기록은 1분마다 다시 읽고, 실행이 끝나면 한 번 더 읽습니다.
- **[필수] 작업과 웹 서버를 분리합니다.**
  - 작업 출력은 파이프가 아니라 파일(`reports/ui_job_*.out`)로 보냅니다.
  - 작업 정보(PID, 출력 파일, 대상 목록)는 `reports/.ui_job.json`에 둡니다.
  - 웹 서버가 재시작되면 살아 있는 작업을 이어받습니다.
  - 이유: 출력을 파이프로 받으면 웹 서버가 재시작될 때 작업이 함께 죽고, 기록도 남지 않습니다.
- **한 번에 하나의 작업만** 실행합니다(이관, 삭제, 인벤토리).
- 확인 창은 화면 안에 그립니다. 브라우저 기본 `confirm`과 `prompt`는 일부 내장 브라우저(예: IDE의 웹뷰)에서 조용히 취소되기 때문입니다.
- 대상 삭제는 "삭제"를 직접 입력해야 실행됩니다. "DB도 삭제"는 한 DB의 결과를 전부 골랐을 때 나타나며 기본 켜짐이고, DB가 비어 있을 때만 지웁니다(다른 테이블이 남아 있으면 DB는 유지).
- 진행 표시는 두 단계를 합쳐 0→100%로 보여줍니다(준비 20%, 이관 80%).

## 8. 성능 설계 원칙

- **처리 시간은 데이터 양보다 명령 기동 비용이 지배합니다.** beeline과 hadoop 명령은 실행할 때마다 JVM이 뜹니다. 작은 테이블이 대부분이면 명령 횟수가 곧 처리 시간입니다.
- **[권장] 묶어서 실행**: 메타정보는 한 세션에 50개씩, 경로 조회는 한 번에 100개씩, 대상 목록은 한 세션에 DB 200개씩 처리합니다.
- **[권장] 빈 테이블 빠른 처리**: 테이블당 명령 1번으로 처리합니다.
- **동시 처리 수(`parallel`)**: 운영 HiveServer2와 원본 클러스터 사양에 맞춰 정합니다. 동시 수를 늘리면 테이블당 시간은 늘고 전체 처리량은 늘어납니다.
- **[권장] 적정 동시 처리 수 찾기**: 실행 중 변경 기능으로 한 실행 안에서 측정합니다.
  1. 작은 값(예: 2)에서 시작해 10~15분마다 2씩 올립니다.
  2. 단계마다 완료 수/분(처리량), 테이블당 평균 시간, 원본과 대상 HiveServer2의 CPU와 메모리, YARN 큐 사용률을 기록합니다.
  3. 처리량이 더 늘지 않거나 테이블당 시간만 늘기 시작하는 지점이 포화점입니다. 적정값은 포화점 바로 아래로 정합니다.
  4. 원본 부하 허용치(운영 담당자와 합의한 CPU, 큐 사용률)를 넘으면 처리량과 상관없이 그 아래로 정합니다.
  - 단계별 비교는 비슷한 크기의 테이블끼리 해야 합니다. 테이블 크기 구성이 바뀌면 처리량도 바뀌기 때문입니다.
  - 근거: 테이블 하나에 JVM과 MapReduce 작업이 3~4개 뜨고, 각각 CPU를 1개 이상 씁니다. 그래서 동시 수가 실행 서버나 큐의 CPU 수에 가까워지면 포화됩니다. 그 이상으로 늘리면 대기만 길어지고, 메모리 사용과 타임아웃 위험이 커집니다.
  - 참고 측정(테스트 환경, CPU 4개): 동시 3~4개에서 CPU가 포화됐고, 6개에서도 처리량은 같았습니다(분당 약 3.8개, 테이블당 CPU 약 63초).
  - **[확인]** 운영에서는 실행 위치(엣지 노드), 원본과 대상 HiveServer2, YARN 큐 중 어디가 먼저 포화되는지 확인합니다.
- **검증 MapReduce 작업이 비쌈**: checksum은 테이블마다 원본 1번, 대상 1번 작업을 띄웁니다. 그 밖의 확인은 작업을 띄우지 않게 합니다(5장 통계 기준 `count(*)`).
  - 참고 측정(테스트 환경, 객체 50개, 동시 5): 통계 기준 `count(*)`를 계획 확인으로 바꾸자 대상 HiveServer2 CPU가 27%, 전체 CPU가 17% 줄었습니다.
- **[확인] 쿼리마다 드는 고정 비용**: 작은 테이블에서는 데이터를 읽는 시간보다 작업 기동(YARN 컨테이너, JVM)이 더 깁니다. 운영 대상 클러스터에서 다음을 쓸 수 있는지 확인합니다. 원본은 운영 부하 때문에 바꾸지 않습니다.
  - `hive.exec.mode.local.auto=true`: 입력이 작은 쿼리를 HiveServer2 서버 안에서 실행(YARN 기동 없음)
  - Tez 엔진과 컨테이너 재사용
- 참고 측정(테스트 환경, 67개 객체 중 빈 테이블 50개): 최적화 전 28분 → 묶음 실행과 빠른 처리 후 약 7분. 운영 수치는 운영에서 다시 측정해야 합니다.

## 9. 남은 과제

1. **[확인]** 1장과 6장의 운영 환경 확인 항목
2. 원본 부하를 줄인 검증 (5장): 원본 통계와 파일 단위 비교
3. 결과 테이블 기록: 일정 건수마다 나눠 쓰기, `run_id` 파티션
4. ACID를 원본 쓰기 없이 처리: major compaction된 base 파일 이용(미시험)
5. 빈 테이블 여러 개를 한 세션에서 생성 (빈 테이블이 많을 때 큰 효과)
6. 큰 테이블: 크기에 따른 매퍼 수, 파티션 단위 복사, 중단 후 재개
7. Hadoop 버전이 다를 때 webhdfs distcp 시험
8. 전환 직전 변경 감지: 이관할 때의 원본 파일 수, 바이트, `ddl_time`을 결과에 남기고, 전환 직전에 지금 원본과 비교해 바뀐 테이블을 다시 이관할 목록으로 내보냄
